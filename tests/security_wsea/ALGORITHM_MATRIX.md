# Algorithm interoperability and adversarial matrix

These sources generate disposable fixtures with real OpenSSL operations and
execute the production verifier. They contain no execution results. Run them
only in the authorized SSH Linux cgroup, through the bounded launcher. The current format is embedded WSEA v2.
Earlier detached-v1 reports and `run.py` fixtures are historical evidence only.

`algorithm_matrix.py --prepare` creates a new private directory, CA-issued
certificates, CRLs, signed modules and a frozen `fixtures.json`. It never resets
an existing policy/state directory. Each execution creates fresh state; ordered
revocation and policy-upgrade cases share state only within their group. All
fixture paths are absolute, so retain the original directory on the Linux host.

The final custom section is `uwvm.wsea.v2`. Signatures authenticate the exact
WASM prefix before that final section. The entire final image, including the
embedded certificate/CRL evidence, is bound to the VM's private execution receipt.
Sidecar files in the disposable producer workspace are fixture-generation inputs;
neither current verifier reads them during module authorization.

The 13 exact algorithms are ES256, ESP256, ES384, ESP384, ES512, ESP512,
Ed25519, PS256, PS384, PS512, RS256, RS384 and RS512. The matrix covers:

- OpenSSL-produced positives and signatures over complete custom sections;
  appended bytes, forged signatures and protected algorithm substitution.
- ECDSA curve binding, fixed raw widths, high S, zero scalars, DER substitution
  and P-521 unused high bits.
- RSA padding confusion, PSS MGF/salt mismatch, SHA1/MD5 fallback, 2048-bit,
  exponent-3 and oversized keys; genuine 4096/8192-bit keys with successful
  RS256 and PS512 signatures; restricted RSA-PSS SPKI rejection. The oversized SPKI and weak-key cases use
  deliberately invalid signature values to reach key admission before math.
- Pure Ed25519 versus real Ed25519ph/ctx signatures, signature lengths, S+L,
  another signing key, Ed448, canonical/small-order R, and real CA-issued,
  explicitly pinned low-order/noncanonical Ed25519 public keys.
- Canonical COSE types/lengths/tag/header, forbidden unprotected fields and
  trailing input; valid certificate/CRL/root DER followed by an extra object or
  garbage inside one PEM block; missing END followed by nested same/other-label
  BEGIN blocks; CA-authenticated RSA absent-NULL, compressed EC point,
  explicit EC curve, Ed25519 NULL-parameter and non-byte-aligned SPKI rejection;
  strict CSV policy sets, unchanged six-field ES256 defaults,
  explicit policy broadening and policy rollback.
- Ed25519 and RSA-PSS certificate/CRL signatures, signer and issuer EKUs,
  certificate/CRL PSS parameter mismatches, authenticated revocation and
  old-good-CRL replay after a durable tombstone; genuinely CA-signed CRLs with
  inconsistent inner/outer algorithms, v1 encoding, and removeFromCRL reason 8.
- Every algorithm has a signed WASI `fd_write` guest and a forged-signature copy
  of the same guest. With `--vm`, positives must emit their fixed marker and
  negatives must not emit any guest marker. Go-produced signatures reuse the
  same guests. The four RSA4096/8192 positives also emit markers.

The Ed25519ph/ctx producer needs OpenSSL 3.5's provider instance API. An absent
helper or unsupported instance produces `BLOCKED`, never a passing coverage
claim. Test-only fixture keys are disposable and must not become trust anchors
outside the generated test directory.

RSA4096/8192 keys are generated by OpenSSL, with elapsed command times recorded.
`--rsa-keygen-timeout` defaults to 600 seconds per large-key producer; a timeout
leaves the corresponding coverage `BLOCKED`, never skipped as a passing case.
The external authorized stage deadline still bounds the complete run. Raw-TBS
SPKI/CRL variants are signed by their original P256 CA and independently checked
by OpenSSL before being submitted to either candidate. OpenSSL CLI and the
Ed25519 variant helper may use different recorded native OpenSSL versions.

Build the native fixture producer and each actual target runner in Linux. Supply
the approved compiler, target sysroot, and OpenSSL include/library paths for that
target. For example, with those shell variables already set by the builder:

```sh
"$NATIVE_CXX" -std=c++20 -O0 -g0 "$REPO/tests/security_wsea/algorithm_fixture_signer.cpp" -I"$NATIVE_OPENSSL/include" -L"$NATIVE_OPENSSL/lib" -Wl,-rpath,"$NATIVE_OPENSSL/lib" -lcrypto -o "$NATIVE_OUTPUT/algorithm_fixture_signer"
"$TARGET_CXX" -std=c++20 -O0 -g0 -DUWVM_WSEA_OPENSSL=1 --sysroot="$SYSROOT" -I"$REPO/src" -I"$TARGET_OPENSSL/include" "$REPO/tests/security_wsea/algorithm_matrix_runner.cpp" -L"$TARGET_OPENSSL/lib" -lcrypto -pthread -o "$TARGET_OUTPUT/algorithm_matrix_runner"
python3 "$REPO/tests/security_wsea/algorithm_matrix.py" --prepare --openssl "$NATIVE_OPENSSL/bin/openssl" --ed-variant-signer "$NATIVE_OUTPUT/algorithm_fixture_signer" --output "$FIXTURES" --require-cgroup
```

These are dynamic-library examples. A bundled static build may place
`libcrypto.a` directly at its output root; use the builder's actual absolute
archive and include paths instead of assuming a `lib/` layout.

The runner accepts `POLICY MODULE [EXPECTED_ID]`; `--identity` executes the
actual target's architecture/OpenSSL identity. A successful verification also
requires the production authorization token to match the exact source buffer.

For every emulated target, supply the actual absolute QEMU argv array, including
an explicit `-L`; pass target `LD_LIBRARY_PATH` through QEMU `-E`. A library-only
sysroot rewrites `open("/")` and breaks the intentional root-fd, no-symlink policy
walk. For these SDKs use `-L /`, followed by the exact frozen target PT_INTERP
loader and `--library-path TARGET_LIBRARIES`, then the target executable. The
report separately records the SDK sysroot, real filesystem prefix and explicit
loader hash. Production path admission remains unchanged.
The runtime receipt is JSON with the exact `target` name, absolute `sysroot` and
`runtime_root`, and `runtime_files: [{"path": "/absolute/file", "sha256": "..."}]`.
List the actual target interpreter,
libcrypto, C/C++ runtime and dependencies; source/provider/ABI metadata may also
be included. Files are hashed and ELF identities checked. The ELF PT_INTERP is
resolved using target-root symlink semantics and must match a frozen loader.

```sh
python3 "$REPO/tests/security_wsea/algorithm_matrix.py" --fixtures "$FIXTURES" --runner "$TARGET_OUTPUT/algorithm_matrix_runner" --target "$TARGET" --execution qemu --exec-prefix-json "$QEMU_ARGV_JSON" --target-sysroot "$SYSROOT" --runtime-root "$TARGET_RUNTIME" --runtime-receipt "$RUNTIME_RECEIPT" --output "$RESULTS/$TARGET" --require-cgroup
```

Add `--vm /absolute/actual-target-uwvm` to repeat cases through the real CLI,
loader, initializer and guest execution. A loader-only probe does not qualify
as `--vm`. Native evidence must explicitly use `--execution native` and an empty
prefix; native execution is never described as QEMU evidence.

| Target | ELF class | Byte order | Required ABI |
| --- | --- | --- | --- |
| aarch64 | 64 | little | LP64 |
| x86_64 | 64 | little | x86-64 |
| i686 | 32 | little | i386 |
| arm | 32 | little | EABI5 soft float |
| armhf | 32 | little | EABI5 hard float |
| armeb | 32 | big | EABI5 hard float (Bootlin provider) |
| aarch64_be | 64 | big | LP64 big endian |

| mips64 | 64 | big | n64 |
| loongarch64 | 64 | little | LP64D |

ROS qualification covers x86_64, i686, aarch64, arm, armhf, armeb and aarch64_be.
Main and stable additionally cover ppc64, mips64 and loongarch64. Native execution
and QEMU x86_64 execution are separate evidence.

The default `--case-profile full` runs every frozen case through the production
C++ verifier and actual VM. Where the security header is byte-identical, the
cross-target driver runs this complete profile once per target, then uses
`--case-profile product` for the other actual repository binaries. That explicit
profile runs all thirteen authenticated guest witnesses and forged counterparts,
real RSA4096/8192 boundaries, policy/revocation transitions, v1 downgrade, missing,
duplicate, truncated, noncanonical and trailing embedded-section cases. Reports
record the available and executed fixture counts; a reduced profile is never
reported as the complete matrix.

The companion `wasm-cosign/test/wsea/algorithm_interop.py` imports the explicitly
supplied matrix driver. It independently sends the entire OpenSSL matrix to Go,
signs all algorithms in Go, and verifies both OpenSSL and Go artifacts in the
actual target C++ runner/optional VM. It also checks CLI policy defaults,
algorithm updates, saved allowlists and whole-module tampering. The native Go
producer/verifier is recorded as host-side evidence. Go's state API is read-only:
fresh interoperability state groups are advanced by explicitly recorded target
C++ authorization/revocation calls between Go checks. Subsequent Go policy
rollback and old-CRL replay checks are cross-layer state evidence; they do not
claim that Go writes state. Standalone matrix runs use separate fresh state.

```sh
python3 "$COSIGN/test/wsea/algorithm_interop.py" --matrix-driver "$REPO/tests/security_wsea/algorithm_matrix.py" --fixtures "$FIXTURES" --go-cli "$NATIVE_OUTPUT/wsea-cli" --runner "$TARGET_OUTPUT/algorithm_matrix_runner" --target "$TARGET" --execution qemu --exec-prefix-json "$QEMU_ARGV_JSON" --target-sysroot "$SYSROOT" --runtime-root "$TARGET_RUNTIME" --runtime-receipt "$RUNTIME_RECEIPT" --output "$RESULTS/interop-$TARGET" --require-cgroup
```

The lightweight Go CLI takes direct subcommands; for the full cosign CLI, also
pass `--go-subcommands-json '["wasm","secure"]'`. Reports include actual argv,
binary and runtime hashes, ELF/ABI metadata, executed identity, fixture hash,
stdout/stderr/return codes and cgroup evidence. A crash, timeout, missing file,
incorrect architecture or missing producer is not a passing negative test.

Execution oracle r4 requires exact Linux exit codes: Go CLI denial `1`, C++
verifier denial `2`, and VM parameter/loading denial `126` or `127`. A security
message followed by a signal or QEMU's translated `128+signal` exit cannot pass.
Success requires exit `0`, plus the guest marker wherever declared. Reports
record expected codes and keep the frozen fixture generator hash separately
from the current execution driver hash. The embedded-v2 fixture manifest is a separate generation from historical
detached fixtures. Its generator hash and the current execution-driver hash are
recorded separately; immutable failed attempts remain available.


`embedded_usage.py` runs a private authenticated HTTPS origin, successful
fetch/verify/VM execution, server/network mutation and refusal before publishing,
direct download bypass followed by VM refusal, post-download mutation and
ordinary unsigned execution without `--secure`. Its private TLS CA does not
modify system trust. Native startup timings include real process startup.

`embedded_receipt.py` and `embedded_receipt_runner.cpp` exercise real receipt
invalidation for content/pointer changes, policy/version floors, authenticated
revocation tombstones, manifest expiry, certificate NotAfter, CRL nextUpdate and
maximum CRL age. Unchanged-buffer reuse avoids repeating PKI work, while these
facts are checked before initialization.

For a cross-built static Go secure CLI, the interop driver also accepts
`--go-exec-prefix-json`. It binds the executable's machine/class/byte order to
the declared target and requires the same recorded QEMU as the C++ VM. Standard
Go has no Linux armeb/aarch64_be target; those VMs still receive signatures from
an independently executed host Go producer. This limitation must remain visible
in the aggregate report.


`warm_key_matrix.py` sends all 277 frozen cases to one production C++ verifier
process using `algorithm_matrix_runner --batch`. Each authorization still loads
its own policy and module. Ordered state groups preserve revocation/policy
transitions. This catches accidental reuse of authorization after successful
RSA mathematical validation, rather than testing each adversarial input in a
new process with an empty key memo.

`multi_module_program.py` signs and verifies thirteen independently named modules
under one policy, then loads the real program with all selections registered
after its preload arguments. It repeats this with six RSA8192 modules sharing a
key. Both scenarios alter the last library's signature after the upper gate
accepted it: the upper gate must refuse it and the VM must independently refuse
before any guest marker. There are 44 explicit command checks per product.

`startup_algorithms.py` alternates ordinary and selected-module native process
startup across all thirteen profiles and genuine RSA4096/8192 cases. It records
every sample, filesystem and ambient load. Cold RSA mathematical validation is
included; a fresh process cannot borrow another process's key memo.

`startup_cosign.py` separately measures the full native `cosign wasm secure
verify` command across the same seventeen profile/key samples. Each sample
starts the complete process and requires JSON `status=VERIFIED`; it includes
CLI initialization and read-only policy/state checks, without network activity.
Keep its recorded load and tmpfs scope visible when comparing results.


`execution_policy.py` checks eighteen ES256/Ed25519 execution-boundary cases:
the upper gate accepts an authentic manifest with no host capability, while the
VM must reject its `fd_write` import before guest entry with normal exit 127.
It also checks explicit ordinary execution, selected symlinks, a legitimate
permission change and refusal to sign beyond the administrator's mask without
modifying the previous file. The earlier trap-based denial remains a retained
failed attempt; it is not counted as a passing denial.

MIPS uses Clang's explicit `-mllvm -mips-tail-calls` with the private hidden
opfunc attributes. The authenticated Debian binutils provider supplies GNU BFD
for its glibc startup objects, with the main ELF linked `-z noexecstack`. This
SDK's glibc nevertheless requests an executable stack for compatibility with
pre-4.8 MIPS kernels; the actual loader `mprotect` is retained in the probe log.
The qualification proves the signature and execution gates under the recorded
Linux/QEMU environment, and does not claim process-wide W^X for this SDK. See
the [glibc compatibility rationale](https://sourceware.org/legacy-ml/libc-alpha/2019-08/msg00479.html).


`openssl_kat.cpp` checks SHA-256/384/512 against the standard `abc` vectors,
including independent and copied digest contexts. MIPS assembly generation in
the unmodified upstream `sha512-mips.pl` probes `MIPSEB` through `$CC -E` without
`CFLAGS`. The source-owned builder therefore puts MIPS target C flags in `CC`
as well as `CFLAGS`. This preserves assembly acceleration while making the
probe observe the actual target. The former cross build's known-answer failure
and corrected target execution are retained separately; an ELF/ABI build pass
alone is not treated as cryptographic qualification.

`arm_empty_concurrent_map.cpp` is a focused ARMv5 runtime regression. A 64-bit
atomic load can use the ARM Linux compare-and-swap helper and therefore needs
writable storage even when the logical value does not change. The former
Boost empty-table sentinel was in `.rodata`; both ordinary and secure guest
execution reproduced a segmentation fault. The source-owned patch makes the
dummy storage writable on pre-ARMv7 targets. Concurrent empty lookups, insertion,
moved-from lookups and lookups after clearing/releasing groups must succeed.
The original small reproducer's crash is retained as a diagnostic control,
never as a successful signature refusal. GCC also documents that an
[atomic load may use compare-and-swap](https://gcc.gnu.org/onlinedocs/gcc-9.1.0/gccint/Standard-Names.html).

The ARMv5 qualification recipe uses an explicit include overlay with the same
patched public vendor header, preserving earlier immutable cohorts and their
dependency hashes. Reports record the overlay's complete dependency paths and
hashes. Other qualified profiles use the unchanged conditional branch. The
overlay source and the original sentinel header are included in final evidence.
The isolated regression explicitly selects `qemu-arm -cpu arm926`; the full
product matrices retain their separately recorded QEMU execution prefixes.

For the Bootlin big-endian ARM SDKs, explicit C include paths follow libstdc++
wrapper paths so that `include_next` reaches the target C library. Clang uses
an 8M constexpr-step budget for the expanded command-line alias table; the three
production Xmake configurations use the same budget for these targets. This is
a compile-time evaluation limit. Reusing a successfully compiled lower-budget
binary preserves its original receipt and still requires identical compiler,
source dependencies, other flags and binary hashes.

`startup_sizes.py` signs genuine ES256/Ed25519 guests with 1, 16 and 64 MiB of
custom-section data. It checks the full cosign first gate, alternates ordinary
and secure native startup with two warmups/five samples, then changes the last
authenticated prefix byte and requires both gates to refuse it without guest
entry. Its 108 command checks and six timing rows retain process/load/tmpfs
scope; these are warm-page observations, not cold-storage latency guarantees.
