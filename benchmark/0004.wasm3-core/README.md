# Core WebAssembly 3.0 performance qualification

The programs in this directory are small, self-checking **new-syntax** workloads. `generate.py` writes WAT with a known final value and `wasm-tools` validates the binary before any sample is recorded. The same `.wasm` file is passed to each supporting VM. A successful exit is required for every semantic and timed sample.

The feature list follows the official [WebAssembly 3.0 change history](https://webassembly.github.io/spec/core/appendix/changes.html), edition dated **2026-09-21**: extended constant expressions, tail calls, exception handling, multiple memories, 64-bit memory and table addresses, typed function references, GC, and relaxed SIMD. The threads/atomics extension is measured separately and in combination with memory64. Static and dynamic controls distinguish the added feature from the older operation where possible. `extended-const-init` changes module initialization, so its per-iteration slope is **not** a measure of initialization cost. The final conformance report must separately identify the official spec-test suite checkout and commit/tree hash; these generated benchmark cases are not that suite.
The same change history also lists profiles and custom text annotations. Those specify execution subsets or parse-time metadata rather than a new runtime instruction; this throughput matrix does not assign them a per-op speed. Their parsing and validation belong in the semantic/front-end suite.

These 32 cases cover performance-relevant feature families and selected instructions, not every Core 3 opcode or type combination. The separate semantic/conformance suite remains necessary for exhaustive syntax and behavior claims; no unmeasured instruction inherits a throughput result from another case in its family. This records the suite asset identity only; the final conformance report must list exactly which files were executed and passed against which product source/binary. The separate semantic suite must record the official spec-test checkout and hash. A successful matrix case never implies that all variants in its family passed validation, execution, code generation, or performance review.

`extended-const-init` executes its new syntax once during instantiation. Its repeated LCG loop is a checksum/control, so the high-minus-low slope is **not** the cost of extended-constant evaluation; report whole-process startup only as a noisy upper bound and keep syntax/semantic qualification separate.

`gc-allocation-ring` exports its table so writes are externally observable. Each iteration allocates a one-field struct, overwrites one of 1024 roots, reads it back, and checks the final LCG result. All but the latest 1024 structs eventually become unreachable; this explicitly exposes **retained garbage** and peak RSS, not just allocation throughput. Java, C#, and JavaScript analogues likewise write a global 1024-entry root ring, verify the same arithmetic, and after the timed loop check every retained object against its expected slot and final LCG value. The Python runner independently verifies the returned state and root checksum. This post-loop check keeps the live roots observable without charging verification to the measured guest loop; intermediate overwritten allocation observability still depends on each runtime's optimization rules. The analogues use different bytecode, object layouts, JITs, and collectors, so they are a qualitative GC/lifetime comparison rather than a same-binary VM ranking. The earlier r38 managed results used the pre-root-check fixture and remain diagnostic history, not this strengthened fixture's timings. The formal same-Wasm allocation-ring group uses 2M/16M checked allocations: the historical 1M copying-collector run was only about 11 ms and cannot support a stable tail ranking. The larger count remains inside the 64 GiB cgroup and reports actual per-process RSS; any high sample under 100 ms stays marked inconclusive. The independent reclamation gate continues to use 100K/1M/10M allocations.

The random-memory cases export the written memory, read a *different*, state-dependent address on every iteration, feed that value back into the next iteration, and finally read and verify a memory cell. ## Isolation and raw evidence

All compilation and timing must occur inside SSH `linux`, Docker `uwvm3-implementation`, cgroup `/sys/fs/cgroup` with `memory.max=68719476736`, `memory.swap.max=0`, and `cpuset.cpus.effective=0,2,4,6,16-31`. `cgroup_preflight` requires that exact four-P-plus-sixteen-E logical-CPU set, saves the per-CPU topology and maximum frequency, and checks the P/E `core_type` when sysfs exposes it. The container currently does **not** expose `topology/core_type`; a read-only `lscpu -e=CPU,MAXMHZ` check on 2026-09-27 showed CPUs 0/2 at 5.6 GHz maximum, 4/6 at 5.8 GHz, and 16–31 at 4.1 GHz, consistent with the assigned P/E map. This frequency evidence does not measure actual clock during samples; the runner records that separately. The lightweight Python harness, including the high-memory polling watchdog, pins itself to E core 16 and records its actual affinity; its timed VM children use `taskset -c 0` for single-thread workloads. The native GC publication diagnostic uses P cores 0,2,4,6 and pins each worker individually. The compiler for that diagnostic runs on E core 16. **Do not run formal measurements while other agents compile or exercise the Windows VM in the shared cgroup.** The runner rejects a missing cgroup or fewer than nine reversed-order pairs.

`run.py` saves binary and tool SHA-256s, cgroup state before/after, exact commands, WAT/Wasm fixtures, each process's complete log and wall time/RSS/user/system CPU, plus paired high-minus-low slopes and tail latency. Each sample is appended immediately to `raw.jsonl` so an interrupted run retains evidence without rewriting an ever-growing JSON array between measurements; a completed run also emits `raw.json`. It alternates low/high order and rotates/reverses the engine order across pairs to distribute clock or temperature drift. `pair-telemetry.jsonl` records the selected P core's available frequency/governor readings, cgroup CPU throttling counters, and exposed thermal sensors before and after each pair; absent host sensor files are recorded as unavailable. Any new cgroup OOM or CPU throttling invalidates the run. For final-source retests, `--require-exact-source` recomputes both products' `src` and `third-parties` fingerprints against their O3 `build.json` before and after timing, retaining both snapshots. Every supplied competitor/version is probed on the actual module: crashes or semantic failures are saved in `failures.json` and excluded from timing, without carrying over a previous version's unsupported-case list; either UWVM product failing is fatal. `--include-gc-collector-matrix` selects Wasmtime's explicitly named `copying`, `drc`, and `null` collectors for GC cases; `null` is a no-reclamation throughput bound, not a functional GC peer. Each GC summary row also states its reclamation qualification: ordinary and ROS currently lack collection; a selected Wasmtime collector still needs the independent RSS gate, DRC does not reclaim cycles, and another engine's throughput alone leaves reclamation unproven. JIT compilation happens in every process; the slope attempts to subtract its fixed startup, while the recorded process time still includes it. A negative slope or high sample under 100 ms is inconclusive and must be rerun with larger counts. `run_gc_publish_scaling.py` compiles the native diagnostic in the cgroup from a saved source copy and requires `--build-json` plus `--expected-source-id`; it recomputes the full source fingerprint before and after the 4-million-object allocation/teardown test and rejects OOM or CPU throttling. It records compiler/source/binary hashes, RSS, and nine AB/BA pairs for one versus two/four workers. `run_gc_stripe_ab.py` uses the same diagnostic to compare frozen unstriped and striped headers in nine reversed-order pairs at one, two, and four P cores. The native diagnostics measure `gc_object_store`, not Wasm execution.

`run_gc_layout_ab.py` is reserved for the proposed single-block object/value allocation experiment. It takes a frozen O3 product and an **isolated overlay** containing only `gc_object.h`, compiles baseline and candidate from the same source and compiler flags, verifies which header each compilation actually included, then alternates nine candidate/baseline pairs at one, two and four P-core workers. The native fixture separately times four million object allocations, ten million checked local mutable-field set/get pairs across 1,024 retained objects, and store teardown, with an independent checksum for the field loop. It keeps raw times, RSS, frequency/thermal readings, source/header/compiler/binary hashes and cgroup counters, plus `llvm-objdump` machine code and `llvm-nm` symbols for both binaries, and rejects source or tool drift, OOM or throttling. Run the exact-SID baseline before this A/B. Even a large allocation win cannot clear the separate reclamation gate or foreign-reference cycle blocker; ASan/LSan and module-lifetime tests are required before proposing a product source change.

`run_gc_layout_edge_linux.py` separately builds the baseline and isolated header with ASan/UBSan/LSan against both product snapshots. Its fixture checks zero-length arrays, 8-byte fields, near-`PTRDIFF_MAX`/`SIZE_MAX` rejection, partial-construction cleanup and foreign leases. Linux `lld --wrap` additionally injects one deterministic large `nothrow new` failure while sanitizers remain enabled: the baseline must fail its second (array) allocation and release the header, while the single-block candidate must fail its one scalar allocation. This tests the `out_of_memory` path without stressing or OOM-killing the shared cgroup. The edge runner and A/B are pending exact-source Linux execution; syntax preparation alone does not qualify the candidate.

## GC implementation finding and optimization gate

The r38 baseline `gc_object_store` allocates each object and value array separately, publishes through two local atomic compare-exchanges, then takes one **process-wide** spin lock to insert into the foreign-object index. Its r38 O3 `struct_new` disassembly shows both allocator calls, two `lock cmpxchgq` instructions, and `xchgb` against `global_lock_`. The subsequent candidate replaces that lock with bucket stripes, as measured below; the two allocations and monotonic `objects_` chain remain. Allocation and RSS growth therefore remain concerns even after the concurrency improvement. This is a GC **reclamation** gap and a deployment blocker for long-lived modules, regardless of a good short-run throughput score.

A bounded optimization stripes the global index lock by hash bucket/cache line while preserving the local membership fast path. `publish` and foreign lookup take the same stripe; weak owner promotion stays inside it; teardown unlinks each node while holding its stripe before freeing. `gc_stripe_stress.cc` checks four-thread publication, cross-module reads and leases, unload, stale handles, and 1,000 teardown-versus-lookup races; the existing `wasm3_gc_object_store.cc` additionally checks forged references and cyclic leases. Both products passed the stress test under AddressSanitizer and LeakSanitizer and passed the existing test. The native 4-million-object nine-pair A/B evidence in `bench-core3-gc-stripe-ab-r38-20260927/` showed median old/new allocation speedups of **0.9994× on one P core**, **1.0407× on two**, and **1.2365× on four**. At four cores median allocation fell from 290.49 to 237.88 ms and p95 from 299.78 to 276.92 ms, while teardown and peak RSS stayed near 169 ms and 492 MiB. This is a useful concurrency improvement, but the four-core absolute scaling remains weak.

**Release blocker: no unreachable-object reclamation.** `gc_object_store::objects_` retains every struct and array until module destruction; the exported 1024-root ring's r38 JIT peak RSS rose from 106.46 MiB at 100,000 allocations to about 169 MiB at one million despite at most 1,024 live roots. This behavior can exhaust a long-lived module's memory, and releasing millions of objects at teardown creates latency. The stripe change does not address it. The code should be called a monotonic managed-object store, not a collector. A safe collector needs precise interpreter/JIT stack maps at every safepoint, roots in globals/tables/host handles and exception payloads, reference-field write barriers, cross-thread stop-the-world or concurrent barriers, cross-module lease/identity handling, and proofs that active readers cannot see reclaimed storage. A two-allocation-to-one object layout can improve allocation throughput separately, but also cannot reclaim garbage. Neither shortcut is sufficient to declare GC production-ready.

`release_check_gc.py` is the **opt-in publishing gate** for this blocker. It runs the same validated exported-root-ring Wasm at 100,000, one million and ten million allocations on ordinary/ROS full JIT and full interpreter, with three independent process samples per point. It requires `--ordinary-source-id` and `--ros-source-id` for the intended frozen release in addition to checking the exact O3 build fingerprints and binary hashes; a historical candidate cannot silently stand in for a final product. It checks cgroup OOM counters, saves all raw logs/RSS, and exits **2** with `FATAL GC reclamation blocker` if the median peak RSS grows more than 64 MiB between the middle and high points. A flat RSS curve by itself does not prove collection, and a staged `--engine` subset cannot pass the complete gate. The current product exposes no authoritative collection count, so even an RSS-only pass exits **3**, records `release_gate_passed=false`, and identifies the missing counter or product modes. The gate can pass only after source-bound positive collection counts are wired into the runner and all four product modes demonstrate bounded RSS. `test_release_check_gc_scope.py` checks those decision rules offline. Default throughput runs remain measurement-only and never hide this release gate. `RELEASE_BLOCKER_GC.md` records the other technical acceptance criteria and evidence.

`generate_exnref_reclamation.py` adds two separate self-checking release probes outside the 32-case throughput matrix: `discarded-exnref` throws a changing i32 payload, catches it as an exnref and drops the reference each iteration; `exnref-aggregate-cycle` throws a struct payload, stores the caught exnref back into that struct, and replaces one of 1,024 exported table roots. Thus old exception instances and old exception↔struct cycles should become unreachable. Both 1,000-step WAT modules parsed and validated with local `wasm-tools`. Ordinary macOS candidate SID `7c9306c8…` then ran both modules under JIT full `instruction` and `unwind`: **4/4 checksum self-checks passed** within a 4 GiB process-tree watchdog (largest measured peak 97,730,560 bytes). The [candidate summary](/Users/liyinan/Documents/MacroModel/src/uwvm2/build/wasm3-evidence/exnref-reclamation-macos-ordinary-7c9306-smoke-v2/summary.json) is SHA-256 `da151c9672bf995282b31fe63f401232fc6200320cf1a2565a4ffa5fbf083459`. This is semantic evidence only; no collection count was measured and the monotonic store does not reclaim these objects. `release_check_exnref_gc.py` is the corresponding pending SSH Linux gate: exact O3 source IDs, two cases × three counts × four full modes, checksum/trap checks, immutable Wasm SHA, RSS growth, optional same-Wasm Wasmtime copying oracle, cgroup OOM check, and hard requirement that each case/mode report a positive real collection count. The current runtime exposes no such count and should fail; a one-case or one-mode subset also fails even if its RSS is flat. `test_release_check_exnref_scope.py` verifies those decision rules. Do not label the generated cyclic graph collected until a final-source run actually forces and counts collection.

`generate_gc_root_survival.py --allocations N --root all --out file.wat` produces a self-checking root-survival test for the future collector. Choices include local, operand stack, table, global, retained exception reference and sixteen simultaneously live locals. `run_gc_root_survival.py` executes it against exact-source O3 ordinary full/lazy/tiered and ROS full modes, with an optional same-Wasm Wasmtime copying oracle, saving hashes, logs, RSS and cgroup state. Formal use passes each `--root` separately to identify the precise failed root. Tiered runs save compiler promotion markers: configuring T2 does not prove that a run entered it. The runner also saves the product's actual CLI fatal for the unsupported `-Rcc tiered -Rcm full` combination. A collector must both survive this fixture **and** demonstrate that a collection actually ran during its allocation burst; passing on today's monotonic store is only a semantic preflight. Host-callback and parked-thread roots need the additional native harness described in `RELEASE_BLOCKER_GC.md`.
