# Release blocker: Core 3 managed objects are not reclaimed

As of the 2026-09-28 candidate sources, `gc_object_store` is a monotonic object store. Every successful `struct.new` or `array.new` adds an object to `objects_`; no code traces reachability or reclaims an object while its module remains live. The destructor releases the chain only at module teardown. This supports the instructions' observable behavior for bounded workloads but is not a garbage collector suitable for long-lived modules.

The self-checking exported 1,024-root ring in `generate.py` replaces a root every iteration. At one million allocations, at most 1,024 objects remain reachable from that table, but ordinary and ROS r38 JIT peak RSS rose from 106.46 MiB at 100,000 allocations to 169.29 and 168.63 MiB at one million. The same module on Wasmtime 48 with an explicitly selected copying collector measured 106.46 MiB at both points in this harness. Raw per-process RSS, 9 reversed-order throughput pairs, exact `.wasm` and binary hashes are in SSH `linux` at `/work/wasm3-resume-20260924/evidence/bench-core3-ring-r38-core-20260927/`. This two-point result demonstrates retention; it does not establish an asymptotic growth rate or compare host process startup overhead. The 4-million-object native store diagnostic peaked near 492 MiB and spent about 145–170 ms in module teardown. Its raw evidence is in `bench-core3-gc-publish-r38-20260927/` and `bench-core3-gc-stripe-ab-r38-20260927/` under the same evidence root.

The 256-stripe foreign-object index improves four-P-core publication by 1.2365× in nine AB/BA pairs without a one-core regression. It does not make objects collectible. Combining the object header and field array into one allocation could reduce the current two allocator calls and help throughput, but it likewise does not resolve unbounded retention.

The opt-in `release_check_gc.py` is an executable gate: the same exported-root-ring module runs at 100,000, one million and ten million allocations on both products' full JIT and interpreter, with three process samples per point. It requires exact O3 source IDs, no cgroup OOM, and at most 64 MiB additional median peak RSS between one and ten million allocations. It prints `FATAL GC reclamation blocker` and exits 2 on failure. The current monotonic source is expected to fail. This gate is separate from ordinary performance collection, which must remain able to report the failure data.

An actual collector must first establish and test these invariants:

1. **Precise roots at every safe point.** The interpreter register ring, JIT locals/operand stack, native spills and tiered transitions must enumerate all live GC references. `unwind` stack traces are not themselves GC stack maps. Host-visible refs, imported/exported globals, tables, exception payloads, pending calls and activation records must participate.
2. **Reference mutation and concurrency.** Stores to structs, arrays, tables, globals and host handles need barriers or equivalent accounting. All Wasm threads must reach a coordinated safe point, or a concurrent collector must prove its barriers and memory ordering. `atomic.wait` and host imports cannot strand unscanned references.
3. **Cross-module lifetime.** A receiving module can retain objects after the originating module unloads. The existing foreign registry, weak-owner promotion, `gc_lease_owner`, externref and exnref bridges must keep identities stable while permitting unreachable cyclic object graphs to die. No object may be removed while a foreign reader can still dereference it; forged and stale handles remain non-dereferenceable. Include an exception payload containing a GC ref whose object refers back to the exception: the [Wasmtime exception/GC design issue](https://github.com/bytecodealliance/wasmtime/issues/11256) explicitly identifies this cycle as requiring collection under the full exceptions standard. That issue is design context, not evidence that the present UWVM has a collector or that the future test already passes.
4. **Bounded reclamation and pauses.** A 1,024-root ring must demonstrate bounded live-heap/RSS across increasing allocation counts; cycles and arrays with reference fields must be collected; stop-the-world pause distribution and module-teardown latency must be measured. Scalar memory and no-GC code paths must retain their current hot-path assembly properties.

These are design and acceptance requirements, not implemented claims. A copying collector with JIT-visible bump allocation is a plausible high-throughput direction; deferred reference counting may offer lower pause times but needs precise stack-root reconciliation and cycle handling. [Wasmtime 48's copying implementation](https://github.com/bytecodealliance/wasmtime/blob/v48.0.2/crates/wasmtime/src/runtime/vm/gc/enabled/copying.rs) exposes bump-allocation state to generated code; [its DRC implementation](https://github.com/bytecodealliance/wasmtime/blob/v48.0.2/crates/wasmtime/src/runtime/vm/gc/enabled/drc.rs) reconciles an over-approximated stack root list with precise roots during sweeping. The [WebAssembly GC proposal](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Overview.md) calls for managed objects independent of linear memory, fast allocation and field access, pay-as-you-go cost, and safe thread interaction. The [current Wasmtime collector comparison](https://docs.wasmtime.dev/api/wasmtime/enum.Collector.html) is 50-dev documentation, not the defaults of the measured v48 binary.
The source of the newer intended Wasmtime 49.0.1 comparator confirms the same concrete mechanisms: its [copying heap](https://github.com/bytecodealliance/wasmtime/blob/v49.0.1/crates/wasmtime/src/runtime/vm/gc/enabled/copying.rs) describes JIT-accessible bump and active-space-end state, a semi-space Cheney worklist, and no read/write barriers; its [DRC sweep](https://github.com/bytecodealliance/wasmtime/blob/v49.0.1/crates/wasmtime/src/runtime/vm/gc/enabled/drc.rs) subtracts precise stack roots from deferred over-approximated roots. The DRC source explicitly says it has no tracing cycle collector, so it cannot satisfy the cyclic-object acceptance gate by itself. These are implementation references, not proof that either collector fits UWVM's raw-reference ABI or multithreaded cross-module ownership model.
Its [store root tracer](https://github.com/bytecodealliance/wasmtime/blob/v49.0.1/crates/wasmtime/src/runtime/store/gc.rs) enumerates Wasm stack maps, globals/tables, instance element segments, user roots and a separately rooted pending exception; this is a concrete checklist for UWVM's currently missing root ABI, not a drop-in implementation. Both the copying and DRC heap `attach` paths assert that their internal GC-heap memory is not shared. Their source therefore does not establish safe shared-heap operation for UWVM's VM-managed multi-worker execution, which needs its own global safepoint/ownership proof.

The other requested Wasm comparators require a narrower interpretation. In the tagged [WasmEdge 0.17.1 module source](https://github.com/WasmEdge/WasmEdge/blob/0.17.1/include/runtime/instance/module.h), `newStruct` and `newArray` append separately allocated instances to module-owned `unique_ptr` vectors under a module lock; the [struct](https://github.com/WasmEdge/WasmEdge/blob/0.17.1/include/runtime/instance/struct.h) and [array](https://github.com/WasmEdge/WasmEdge/blob/0.17.1/include/runtime/instance/array.h) each hold a value vector. This is not evidence of a tracing collector, and its measured syntax support must not be ranked as collected-GC performance without an observed-collection/RSS gate. [WAVM's `ObjectGC.cpp`](https://github.com/WAVM/WAVM/blob/master/Lib/Runtime/ObjectGC.cpp) marks and sweeps compartment runtime objects such as instances, tables, globals and memories; its enumerated object kinds do not include Core 3 struct/array aggregates. That useful object-graph example cannot be presented as a Wasm-GC aggregate collector. The official Wasmer **v7.4.2** source enables wasmparser's `GC_TYPES` validation bit in its [common compiler](https://github.com/wasmerio/wasmer/blob/v7.4.2/lib/compiler/src/compiler.rs), but its [common type-section translator](https://github.com/wasmerio/wasmer/blob/v7.4.2/lib/compiler/src/translator/sections.rs) calls `into_iter_err_on_gc_types()` and its [Cranelift operator translator](https://github.com/wasmerio/wasmer/blob/v7.4.2/lib/compiler-cranelift/src/translator/code_translator.rs) has no implementation of `struct.new`/`array.new`. This source audit predicts that our aggregate-GC fixture will be unsupported; it is **not** a substitute for the exact v7.4.2 CLI's executable/semantic probe, which must retain its actual error log and exclude unsupported cells. Only a versioned, self-checking same-Wasm run can admit any of these engines into an equivalent comparison.

Managed-VM sources make the sequencing and performance tradeoff concrete. [HotSpot's OopMap](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/compiler/oopMap.hpp) records reference-bearing registers and stack slots at safepoints; its [thread safepoint protocol](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/runtime/safepoint.hpp) distinguishes running, native, blocked and parked threads. These are directly relevant to UWVM's JIT SSA values, interpreter ring, host calls and `atomic.wait`. [HotSpot's allocator](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/gc/shared/memAllocator.cpp) and [CoreCLR's per-thread allocation contexts](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/garbage-collection.md) demonstrate amortized, thread-local small-object allocation. That is a plausible **second** performance step after exact roots and safe reclamation; a thread-local bump pointer alone would preserve the current unbounded-retention bug.

For a later concurrent or generational design, [HotSpot G1's SATB/card barriers](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/gc/g1/g1BarrierSet.hpp), [its C2 barrier-elision logic](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/gc/g1/c2/g1BarrierSetC2.cpp), [ZGC's colored-pointer load/store state and self-healing](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/gc/z/zBarrier.inline.hpp), and [CoreCLR's assembly-level write-barrier design](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/jit/GC-write-barriers.md) all show that low pause times consume mutator instructions and require a precise reference representation. UWVM should first measure a correct stop-the-world collector's pause distribution, then choose the smallest barrier scheme justified by that data; importing ZGC's pointer bits into its current raw cross-module reference ABI would be unsafe without redesign and proof. The managed-language Java/.NET/Node ring workloads also have different type semantics, optimizing compilers, heap policies and warmup, so they are architectural analogues rather than a same-Wasm ranking. The planned GraalVM CE comparator runs Java **on HotSpot G1**; [GraalVM's Native Image GC options](https://www.graalvm.org/dev/reference-manual/native-image/optimizations-and-performance/MemoryManagement/) describe a different runtime and are not evidence about that Java process.

## Implementable collector path and ABI decisions

The least disruptive first collector is **precise, stop-the-world, non-moving mark/sweep**. It keeps the current aggregate address stable while establishing the correctness machinery that a later copying collector also needs. The implementation sequence should be:

The expected hot-path cost must be measured, not assumed. With a fully coordinated stop-the-world phase, ordinary local struct/array reads and writes need no *concurrent-marking* barrier; their current checked-token lookup, null/type/bounds tests and resulting machine code are the baseline. Both products' identical `single_func_gc_emit.h` currently lower each aggregate get/set through a generic host bridge: generated code clears and fills input/output slots, calls `llvm_jit_gc_aggregate_bridge`, and the bridge copies operands again before dispatching by opcode into the store. This per-access bridge cost is separate from allocation and must be measured with the 1,024-object dynamic heap-field fixtures and actual JIT disassembly. A fixed-arity field bridge is a candidate optimization only if it preserves forged/stale-token rejection, foreign owner promotion and exact collection safepoints; an inlined local-token path needs a further memory-safety proof. Allocation needs a threshold check and a safepoint-aware cold path; exact JIT root maps may introduce live-reference spills at safepoints, while a poll on call/loop paths can add branches even when no collection occurs. A full non-moving mark/sweep traces the reachable reference graph and visits allocated-object metadata, so increasing retained roots or the heap size can lengthen pauses; free-list reuse and fragmentation then need measurement. A one-block object layout removes an allocator call but cannot by itself reduce retained garbage or prove safe sweeping. At each implementation stage, compare baseline and candidate generated assembly, local field ns/op, allocation ns/object, 1/4-P throughput, RSS plateau, teardown time and actual collection pause p50/p95/p99 under matched source-bound workloads. `Collector::Null` is a useful overhead lower bound, not a functioning reclamation comparator.

1. Define a root-enumeration ABI before freeing any object. At every allocation, call, host transition, exception throw/catch, tier transition and other safepoint, the LLVM JIT must emit exact live-reference locations for SSA values that may reside in registers, spills or stack slots; an `unwind` call-stack record is not a GC stack map. The interpreter's register ring needs exact tagged reference slots and frame boundaries for full/lazy execution. Add explicit roots for globals, tables, imports/exports, host handles, exception payloads, pending calls and suspended activations. Root-map tests must force a ref through each location and then trigger collection.
   [LLVM's GC interface](https://llvm.org/docs/GarbageCollection.html) supplies compiler metadata, not a collector. Prototype `gc.statepoint` and `RewriteStatepointsForGC` using the actual bundled LLVM 23 headers, lower representative full/lazy/tiered functions to JIT objects, decode the emitted StackMap section, and compare every location against the live-reference set in the IR at allocation, call, cold-block, table operation, exception and tier-transition safepoints. [LLVM's statepoint documentation](https://llvm.org/docs/Statepoints.html) says a non-moving collector still needs exact locations, and warns that explicit `alloca` root regions are not handled by `RewriteStatepointsForGC`; do not assume that spilling refs into an `alloca` makes them visible. Confirm the platform object/stack-map format on Linux, macOS and Windows before integrating the collector. Runtime heap tracing, thread coordination and reclamation remain UWVM's responsibility.
   An exploratory local `LLVM 23.0.0git` IR probe using `opt -passes=rewrite-statepoints-for-gc`, `llc -filetype=obj` and `llvm-readobj --stackmap` found that a live `ptr addrspace(1)` crossing a call produced `gc-live` and five stack-map locations (including an indirect root), whereas an equivalent live `i64` reference carrier produced only three constant locations and **no** root. This held for Mach-O arm64 (the root was `R#31+8`), ELF x86-64, COFF x86-64 and ELF RISC-V64. The i686 ELF object probe stopped at an unsupported relocation type and has **not** qualified that format; it is not evidence of an i386 product failure. All of this is toolchain-behavior evidence, **not** either product's generated object code or proof about the final bundled LLVM 23 stable build. The present integer/structured GC-reference representation cannot be assumed to become a precise root merely by enabling that pass; define and validate an explicit GC address-space or equivalent root-materialization ABI in ordinary and ROS JIT output on each target object format.
2. Coordinate every VM-managed Wasm thread at a safepoint before tracing or sweeping. A thread in `atomic.wait`, a blocking host import, or a host-to-Wasm reentrant call must either publish an exact, stable activation-root snapshot or rejoin the handshake; it cannot remain an unscanned running mutator. Collection must not hold bucket locks while waiting for threads. Only a validated stop-the-world protocol permits the initial collector to avoid per-field concurrent write barriers; adding concurrent marking later requires barriers and a new proof. This design must respect the existing thread manager's shutdown and module lease rules.
3. Trace one cross-module object graph from the enumerated roots, following nullable struct/array fields, exception payloads, bridge tokens, and rooted global/table entries across arena boundaries. Replace object-field-owned strong `shared_ptr` arena leases with collector-managed graph edges; otherwise A.field→B and B.field→A can retain both stores forever even after all external roots disappear. The same issue applies to `extern_bridge::inner_owner` if A wraps B's aggregate while B wraps A's. A field overwritten by null must cease retaining its previous foreign store after the relevant collection. Keep host/module leases only for genuinely external live handles. The native `gc_foreign_field_cycle.cc` runner checks all three lifetimes separately under ASan/LSan; its weak-pointer result is decisive even if process-global registry pointers make LSan under-report a cycle.
   The present `make_exn_reference` also registers every newly issued exception token in the store's `exn_roots_` with `root_count=1` until reset/teardown. A collector must retire tokens after their **actual** interpreter/JIT/table/global/host roots disappear; treating every historical `catch_ref` as a permanent module root would retain exception payloads and any GC objects they reference, even if aggregate sweeping were added. The test-only `generate_exnref_reclamation.py` creates discarded-exnref and `exnref` ↔ aggregate-cycle modules; `release_check_exnref_gc.py` requires bounded RSS plus a positive, source-bound collection count in both cases and all four full modes. The generated modules passed WAT parse/validate; the current monotonic runtime has no collection counter, and the Linux release gate remains pending and expected to fail.

4. Sweep only after all readers are quiescent. The current local `membership_buckets_` and process-wide `global_buckets_` are designed for monotonic objects: deleting a node while a lock-free local reader traverses it is unsafe. The new never-reused opaque token prevents native-address ABA but does not supply retirement or a traced live/dead decision. Under the initial stop-the-world design, unlink each retiring node from its global stripe and local membership index while all mutators are parked, then free it only after no checked reader can still hold its native address. Assert that forged/stale tokens fail before dereference and retain the checked owner-promotion rule for foreign readers. Module teardown must use the same retirement protocol. A concurrent collector would additionally need an epoch/hazard or equivalent reader-quiescence proof.
5. Only after the non-moving collector passes the semantic and RSS gates, evaluate a copying allocator. [Wasmtime 48's copying source](https://github.com/bytecodealliance/wasmtime/blob/v48.0.2/crates/wasmtime/src/runtime/vm/gc/enabled/copying.rs) documents semi-space bump allocation and JIT-accessible bump-pointer state; that is a relevant fast-allocation reference, but UWVM's opaque guest token still indexes native object nodes that cannot simply move without a forwarding/indirection ABI and full root updates. The foreign index and bridge identities also need a movement proof. [Wasmtime 48's DRC source](https://github.com/bytecodealliance/wasmtime/blob/v48.0.2/crates/wasmtime/src/runtime/vm/gc/enabled/drc.rs) instead shows deferred root accounting and precise-root reconciliation, but per-reference accounting and cyclic object graphs require separate acceptance tests. Neither algorithm can be selected from the 1024-root throughput number alone.

The current checked aggregate handle is already a process-unique, non-address **opaque token**, represented in the existing pointer-sized carrier but never dereferenced. This matches the [Core 3 runtime's abstract addresses](https://webassembly.github.io/spec/core/exec/runtime.html#addresses): they are dynamic, globally unique object identities, not offsets into linear memory or required native pointers; [`ref.eq` compares reference identity](https://webassembly.github.io/spec/core/exec/instructions.html#ref-eq). Both products reserve 1,024 token IDs per thread, refuse allocation before the `uintptr_t` counter wraps (including on `i386`), and compare the token against the local membership or locked foreign index before reading an object. Thus reuse of a native allocation address does not by itself make a stale handle alias a new object. This is an implemented identity improvement, **not** a collector: objects and their local membership-chain links remain published until module teardown, the foreign index only unlinks during teardown, and no live object's token is retired by tracing. A future sweep must unlink every dead token from both indexes while all readers are quiescent, reject stale/forged handles, preserve cross-module owner promotion under the bucket stripe, and never recycle an issued token. The token change still needs final-product and Linux/QEMU semantic, stale-handle and 1/2/4-P performance qualification; the candidate-source Mac result below does not cover those. Measure allocation with the current block reservation before adding any further per-object global counter or slot indirection; test `i386` exhaustion as an explicit failure, not wraparound. [Wasmtime's indexed GC-heap reference path](https://docs.wasmtime.dev/api/src/wasmtime/runtime/gc/enabled/externref.rs.html) illustrates a checked-offset alternative, while its [rooted host-reference API](https://docs.wasmtime.dev/api/wasmtime/struct.Rooted.html) makes external root scope explicit; those links describe current 50-dev code/API rather than the measured 48 or intended 49 binary. Opaque identity does not replace exact roots, coordinated safepoints, reclamation, or cross-module lifetime handling.

This last requirement has a concrete precedent, not an assertion about either current VM: historical Wasmtime/Cranelift advisories [GHSA-gwc9-348x-qwv2](https://github.com/bytecodealliance/wasmtime/security/advisories/GHSA-gwc9-348x-qwv2) and [GHSA-5fhj-g3p3-pq9g](https://github.com/bytecodealliance/wasmtime/security/advisories/GHSA-5fhj-g3p3-pq9g) describe patched 2022 use-after-free bugs from missing stack maps in cold blocks and around reference/table operations. A future UWVM collector gate therefore must count actual collections, inspect maps in cold blocks and table paths, and fuzz live refs across calls, exceptions and tier changes; a passing run with zero collections is invalid. Allocation throughput has a separate, staged optimization path. The current object header and value array use two allocations; after a source-bound A/B and alignment/lifetime proof, a single aligned allocation could hold the header followed by correctly constructed field values, with one matching destructor/deallocation path, checked size arithmetic, zero-length array behavior, OOM behavior, foreign leases, and ASan coverage. A per-store bump arena could amortize allocator overhead, but a monotonic arena alone worsens the RSS blocker; it needs the collector's sweep/reuse protocol before production. A JIT allocation fast path should use validated per-store bump/end state and branch to a safepoint-aware slow path on exhaustion, with all live references in precise maps. It must not bypass foreign publication, write barriers, or object identity checks.
