# VTune CLI diagnosis for current full JIT

This is a development profiling protocol. Temperature is recorded only, per
the latest user instruction. Frequency, CPU placement, process identity and
host activity remain evidence. Profiled wall time is not an engine ranking.
The exact installed VTune version, supported knobs and successful collection
must come from Linux receipts; the commands below are not execution receipts.

## Three independent measurement contracts

Unprofiled diagnostics record actual guest execution time, process wall time,
`wait4` user/system CPU time, maximum RSS, sampled frequency and host P0/SMT
activity. Only their pinned fixture checks, source/ELF closure and actual
quality controls can qualify them. They do not supply hardware instruction
counts. The [r9 long and serial controls](R9_LONG_GC_DIAGNOSTIC_20261002.md)
remain r9 evidence after later source changes.

VTune hardware Hotspots supplies sampled self time and stacks; hardware
Microarchitecture Exploration supplies its own event-derived metrics. Their
profiler overhead, multiplexing, truncated stacks and report scope remain
explicit. Neither profiler launch wall time nor sampled function time replaces
unprofiled execution time. Hardware is now available; no software profiling
fallback is part of the current measurement contract.

The separate [pure hardware counting runner](run_current_pcore_hw_counting.py)
uses an exact same-PMU group `{cpu_core/cycles/,cpu_core/instructions/}`,
`perf stat --no-scale --no-inherit -j -vv`, and an existing single-TID P0
guest. It performs no sampling, no software events and no system-wide
counting. Linux documents raw counting, PID attachment and control ACKs in
[perf-stat](https://raw.githubusercontent.com/torvalds/linux/master/tools/perf/Documentation/perf-stat.txt),
and same-PMU grouping on hybrid CPUs in
[intel-hybrid](https://raw.githubusercontent.com/torvalds/linux/master/tools/perf/Documentation/intel-hybrid.txt).
The guest remains stopped until the actual `enable` command receives `ack`;
the controller then releases it. Perf and guest are separate directly owned
children authenticated by original PIDFD, birth, ancestry, UID, cgroup,
affinity and actual executable/argv. Only the exact owned perf receives
SIGINT after guest retirement. The old long runner's closed roster is unchanged.

These counters cover the whole guest, including startup and JIT compilation;
they are not Wasm-only ROI counters. The result separately retains the
enable-ACK-to-retirement wall interval, guest wall and internal guest duration,
and actual raw `time_enabled`/`time_running`. JSON `event-runtime` supplies
running time, while `pcnt-running` is rounded; the
[Linux display implementation](https://raw.githubusercontent.com/torvalds/linux/master/tools/perf/util/stat-display.c)
does not expose exact enabled time in that field. Exact verbose raw values
must be observed and cross-checked, never reconstructed from a percentage.
The parser accepts the actual stat-output or stderr location, records source,
rejects conflicting/duplicate rows, and leaves unsupported formats unqualified.
At least 99% exact running/enabled is a counter-quality condition, separate
from correctness, frequency observations and engine timing. The four-command
pilot supplies no engine ranking or complete release acceptance.

## Two independent collections

Hotspots locates time in native collector/refill functions versus generated
code. Hardware sampling uses the installed PMU; unavailable hardware remains
a failed collection with its actual error receipt.
Then collect Microarchitecture Exploration to explain the dominant region's
retiring, front-end, speculation and back-end metrics. Intel documents the
analysis name `uarch-exploration`; `general-exploration` is deprecated.

These are CLI templates for the keeper's owned profiling process tree inside
the existing 64GiB/swap-zero sandbox. `CORE3_GUEST_ARGV` is a Bash array of the
actual pinned product command including its `taskset -c 0`. The profiler and
controller use E16; guest threads use P0. Do not insert VTune into the ordinary
diagnostic runner, whose exact process roster deliberately excludes it.

```sh
taskset -c 16 "$CORE3_VTUNE_BIN" -collect hotspots \
  -knob sampling-mode=hw -result-dir "$CORE3_HOTSPOTS_RESULT" \
  -- "${CORE3_GUEST_ARGV[@]}"

taskset -c 16 "$CORE3_VTUNE_BIN" -collect uarch-exploration \
  -result-dir "$CORE3_UARCH_RESULT" -- "${CORE3_GUEST_ARGV[@]}"
```

Add stack collection or `pmu-collection-mode=summary` only when installed help
confirms them and save the exact settings. Record multiplexing, sample count,
unsupported events and permissions failures. Never turn a failed hardware
collection into invented hardware metrics. The keeper owns PIDFD cleanup,
deadlines, explicit profiler-descendant admission and CPU/cgroup verification;
unknown host processes are observed and never signaled.

[Intel's same-container procedure](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2026-0/container-option-1.html)
supports launch analysis. If only host VTune is available, use the documented
[host-to-container procedure](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2026-0/container-option-3.html),
authenticate the guest's exact host PID via namespace mapping/birth/cgroup, and
label attach limitations. Container/driver configuration must be actual keeper
evidence; this document does not claim existing capabilities or change them.

## Reports and attribution

Save summary and function Hotspots reports, using the installed report help for
CSV grouping and filters. Intel's [report reference](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2026-0/report.html)
describes command-line reports. Minimal report templates are:

```sh
"$CORE3_VTUNE_BIN" -report summary -r "$CORE3_HOTSPOTS_RESULT"
"$CORE3_VTUNE_BIN" -report hotspots -r "$CORE3_HOTSPOTS_RESULT"
"$CORE3_VTUNE_BIN" -report summary -r "$CORE3_UARCH_RESULT"
```

Keep LLVM optimization/materialization time separate from `Total WASM execution
time`. For each product report guest nanoseconds, wall/CPU/RSS, real GC counts,
frequency distribution, and host activity alongside native collector/refill
sample time. Report anonymous JIT samples as anonymous until actual symbol
registration or loaded-range evidence proves an identity. Current source has a
private code-range listener; that is not automatically VTune registration.
[Intel's JIT API](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2026-0/jit-profiling-api.html)
requires code-generator reports before execution and documents event-based JIT
profiling with Launch Application. A separate diagnostic build may use LLVM's
Intel listener if the installed LLVM supports it. Its hash and sample mapping
must be retained; do not substitute that build's timing for the baseline ELF.

The pinned ring writes a newly allocated struct to a table slot and immediately
reads the same slot. Older table roots affect GC liveness, but are not the
per-iteration read target. Inspect actual loop assembly and sample attribution
before blaming old-range fallback or enabling more experimental macros.
