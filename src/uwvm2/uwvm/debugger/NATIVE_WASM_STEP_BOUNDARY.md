# Wasm-only native step boundary

This independent short-term safety patch is based on current production before the separate actual-target VIEW52 candidate. It changes no normal LLVM-full guest instruction or OS backend, module parser or Wasm validator. SI and NI first copy one complete actual Wasm function through the existing canonical private capture, actual pause/domain, publication and code-owner lifetime transaction. Two MC contexts are created once for that query. The owned image is at most 64 KiB, forward decoding is at most 8192 instruction boundaries, and malformed/truncated/unrecognized bytes refuse without releasing the stop.

An ordinary SI or NI requires both the current instruction and its fallthrough to be exact forward-decoded boundaries inside that same actual Wasm function. SI may also execute an actual direct branch only if its decoded destination is a boundary in that exact owner; conditional branches require the fallthrough too. Target MC flags, system/trap state changes, unmodelled effects and indirect transfers do not qualify as ordinary or direct branch execution. A numeric destination and MC classification remain DATA, not an authority to operate on a host address.

Calls and returns remain unavailable until actual Wasm callee/caller ownership and continuation authority are implemented. This prevents the old SI path from first executing a host/VM instruction and only afterwards discovering an out-of-owner PC. There is no widened engine text range, arbitrary SP read, raw native memory interface, PC modification or claim that DI describes exact guest state. Missing complete owner copies also refuse.

The new MC corpus checks actual X86 decode plus same-owner conditional edges, inside-instruction destinations, owner-end fallthrough, host call refusal, return refusal and POPF TF protection. It does not claim a hardware trap. The runtime fixture uses a real Core3 GC/nondefaultable-local/return-call module, actual production full-JIT/controller/trap/GPRs and a call-or-return SI refusal with unchanged stop and registers. Missing actual positive/control evidence is FAIL. Both products and both instruction/unwind policies need fresh runtime/producer/main and module closures in the Linux keeper's 64 GiB cgroup; no Mac native execution is authorized.

Later cursor work must bind the actual original pause capture separately from the current native function owner. A callee grant must come from the runtime decoding the same authenticated current bytes and resolving a real Wasm entry in that same current/retained engine generation. It must hold strong owner lifetime, exact loaded entry/range, participant/native thread/stop/epoch and expected current PC, and commit the backend range plus cursor identity before allowing a target instruction to execute. Actual returns require a private physical call/continuation chain; no guessed stack pointer or DWARF-only logical frame grants that authority. Host next-over may use ordinary execution to a proven Wasm continuation, never machine stepping or examining VM instructions. Finish/NI-call capability is still pending.

GDB's instruction-step, instruction-next and finish semantics are described in the [official manual](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Continuing-and-Stepping.html); the [official LLDB map](https://lldb.llvm.org/use/map.html) distinguishes equivalent command operations. uwvm deliberately restricts execution to authenticated Wasm-generated context and does not expose the VM as a debug target. Source review and tests in this packet are not native qualification.

The 2026-10-04 additive check compares the actual completion PC with the one or two successors already proven before the gate opened. A mismatch does not publish a native JIT stop. This is protocol defense, not a substitute for refusing escape before execution. The actual-MC corpus includes all reported indirect bridge-call encodings, indirect jumps, return variants, system/trap operations, REP/LOCK, MOV SS/LSS/POPF and a positive ordinary SIMD fallthrough. These are bounded copied-byte DATA tests; real CLI/DAP and hardware execution qualification remains separate.

References: [Intel SDM](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html), [LLVM MCInstrDesc](https://llvm.org/docs/doxygen/classllvm_1_1MCInstrDesc.html).
