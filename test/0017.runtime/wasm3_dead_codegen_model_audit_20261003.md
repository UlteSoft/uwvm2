# Core 3 dead execution keeps a complete compiler accounting stack

v6 fixes a source-proven bounds defect in the interpreter translator. A nested unreachable block can end with a declared multi-value tuple even though no execution edge reaches it. The validator correctly reconstructs those types, while the physical stack had no corresponding values. A later i32.const appended one physical entry and select committed two pops: the old commit loop checked only that the unchanged vector was nonempty and indexed `size - 1 - i` on its second iteration. The same mismatch occurs when push_ctrl reifies parameters after an unreachable parent and when else restores that dead pre-entry snapshot. This is a compile-time host bounds issue; no local native failure or speedup has been claimed.

The new compiler-only helper copies specification-proven carriers to a memory-only physical accounting model only when actual `codegen_reachable` is false. It resets ring positions and cached counts, records the physical memory count and emits no opfunc, bytecode, spill, fill, guest load, guard or call. Its three call sites follow declaration-typed push_ctrl, complete else semantic/snapshot restoration, and complete end ordinary/EH incoming-edge merge. A real incoming edge retains its saved ring contract. This synthetic accounting stack is not a runtime value, type identity permission, checkpoint or resumable frame.

`stacktop_commit_pop_n` proves the entire suffix (`n <= physical_size`) before any indexed read or count change. Since the vector is unchanged during the commit loop and `i < n`, `physical_size - 1 - i` is in bounds. An unexpected failure terminates as a compiler invariant; it does not clamp a Wasm stack effect, bypass grammar/feature/type checks or accept an invalid module. Existing polymorphic validation remains independent and the authoritative semantic stack is never restored from physical carriers.

The nine independent WAT regressions include multi-result select, mixed numeric/non-defaultable i31/v128 results, typed block/loop/if parameters, explicit and implicit else, a real outer-live-else value47 check, and wrong-heap/nullable typed-select rejection. Every `_start` calls its probe, so full and lazy translation must actually handle that body. The seven valid modules are expected to validate; six intentionally trap unreachable when run and the outer-live-else module succeeds. The two invalid modules must produce a genuine validation error. This also corrects only the reachability of the three prior v5-r2 dead probes in the live runner; the v5-r2 immutable archive remains unchanged.

The C++ component consumes actual wasm-tools-assembled source bytes, parses and initializes them, and compares pure validation with byref plus merged ring1/2/3 translation. Its static expectation is199 checks for all9 fixtures. It uses the complete imported-function prefix plus body index for the pure API. It catches only fast_io parse-domain invalid failures as invalid Wasm; native/OOM failures cannot count as specification rejection. The component compiles bodies; the CLI controls provide actual Wasm execution. First run the default/current macro vector, then the already specified32 combine/delay vectors. Run the component separately with AddressSanitizer+UndefinedBehaviorSanitizer to detect host bounds defects. Sanitizer/codegen capture runs are untimed. No source check, fixed macro vector, counter expectation or sanitizer plan is actual native/ASM/musttail/performance evidence.

Only int emit-helper/control/validation-dispatch source changed; no pure wasm1p1/wasm2 validator, LLVM option, GC store, runtime ABI, host bridge or executable-permission API changed. v2/v3-r2/v4/v5-r2 snapshots stay immutable; a joint compiler source must apply precise leaf deltas instead of replacing later debug/checkpoint files with old whole headers.

Primary rules: [Core 3 validation algorithm](https://webassembly.github.io/spec/core/appendix/algorithm.html) and [control instruction validation](https://webassembly.github.io/spec/core/valid/instructions.html). They separately track declaration-typed stacks and control bottom; the physical register model is an implementation detail.
