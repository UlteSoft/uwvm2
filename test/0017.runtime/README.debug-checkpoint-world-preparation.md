# Checkpoint world preparation

The host-only llvm_jit_checkpoint_prepare_instance_host_api(ticket, captures, request) performs a cold preparation rehearsal in full LLVM mode. It canonicalizes both capture registries, authenticates the complete current paused cohort, and keeps the actual execution lease, closed host admission, exclusive GC access and publication guard throughout census and preparation.

The request carries a recording label, graph limits, a native allocation payload budget and an original-source byte budget, and maximum_private_root_frames for actual cold TLS record installation. It is not a saved-file identity or execution token. The manager copies a fresh current-instance graph itself; callers cannot supply a graph or native addresses.

Preparation privately copies and reparses each actual owned original source, builds a separate resource registry, relocates instance/import aliases, allocates GC shells before filling cycles, restores memories, tables, globals and passive segment liveness, and reconstructs external wrappers and exception diagnostics. Effective replacement bodies retain their actual committed function generations. All defined functions then pass the same authoritative validator/lowering path and real MCJIT preparation, including exact loaded typed/raw and ABI2 resumer entries.

Every saved runnable thread is now prepared root-to-leaf against its fresh engine plan. A unique actual site must match the saved opcode, phase, generation, locals, operands, control/handler counts and return offset. Exact types, raw numeric/v128 bits, uninitialized nondefaultable locals and saved if parameters are reconstructed; references relocate to candidate GC/function/exception/extern objects. Control layouts and lexical handler tag identities are checked. Awaiting callers retain a fresh compiler-sealed child-return projection, and each child result declaration is checked in the real candidate module type contexts. Complete input and retained-root carriers, result carrier capacity, packed result ABI layout, payloads and flags are allocated before success. The carriers are private owned DATA. A separate cold scope now installs genuine root_frame records on the actual calling native thread, verifies only its owned prefix, and removes the records in LIFO order. It never fabricates a guest activation or restored-worker enrollment.

The result contains diagnostic DATA only: status, graph error, module/engine/function counts, prepared thread/frame/input-root-carrier counts, logical native payload bytes and internal refusal codes. Root-carrier counts include initialized null/i31 reference slots and exclude unused result capacity. prepared_and_discarded means every candidate engine and frame/root packet was prepared and all candidates were destroyed before returning. The additional validated_private_root_scopes/installed_private_root_frames/installed_private_root_carriers/private_root_chain_restored fields describe actual cold installation and removal. No executable owner, entry address, native range, source pin, root-installation capability or lease is returned. No old-world drain, VM epoch change, source seal or joint publication occurs.

The current finite observation profile (policy 13) may produce a private resumable compilation profile (policy 17) only with identical schema, ABI, slot width and every budget/workspace field. Unlimited observation frame budgets are refused for resumable preparation rather than silently changed. Instruction and unwind preparation use the actual runtime stack policy.

The native payload budget accounts for charged logical owned allocations, not allocator overhead, parser/LLVM workspace or the retained original instance. Runtime preparation must therefore still run under the external process memory limits used for qualification.

## Native fixtures

- debug_checkpoint_complete_instance_runtime.cc: two real paused episodes with GC cycles/shared aliases, packed/reference arrays, v128, extern wrappers, exceptions/traces, sparse memory64 and passive segment liveness.
- debug_checkpoint_complete_preload_runtime.cc: the same two-thread graph across a main module and a preload, including imported resource aliases and cross-module type contexts.
- debug_checkpoint_actual_generation2_nested_continuation_runtime.cc: prepares actual committed generation-2 replacement bodies both on the original nested pause and on a newly paused retained-world resumed call chain.

The instance fixtures reject empty labels, duplicate/incomplete captures, old tickets/capture episodes, a one-byte native budget and an insufficient original-source budget. A budget one byte below a successful preparation's charged payload refuses during frame/root preparation after every genuine candidate engine is ready; the preload fixture exercises rollback of both engines. They recapture and check the original state after rollback, resume original guests and require their expected result.

Only genuinely captured runnable threads are prepared. Parked-import/atomic-wait threads and in-flight exception-continuation frames remain refused. The new frame/root-carrier code has no platform-specific system calls; executable ABI and native engine availability remain independently gated, and this round qualifies Linux native instruction/unwind only.

These tests do not establish complete-instance execution restore. Cold candidate root installation/removal is now implemented; installing roots on actual restored startup workers, joint world publication and closed-startup worker enrollment remain separate work. Retained-instance physical native retirement/join is documented separately in README.debug-checkpoint-native-cohort-retirement.md. Optional same-stop WASIp1 candidate preparation is documented in README.debug-checkpoint-joint-preparation.md; external I/O effects remain outside rollback. It does not expand ASM debugging beyond guest JIT code, stack or memory.

Private native-thread root enrollment is additionally rehearsed on actual FastIO workers. The full cohort holds its real roots simultaneously behind a private release gate; each worker removes its own prefix and is physically joined before engine/source/store teardown. maximum_private_root_workers and the existing native payload quota bound all worker storage before OS launch. The new worker diagnostic fields describe this private cohort only; joint publication, closed-startup execution enrollment and whole-instance restore remain unfinished. See README.debug-checkpoint-private-roots.md.
