# Core 3 blocktype single-decode runtime resolver (source v3)

The integrated LLVM full validator already decoded each control blocktype, applied the CLI feature policy and checked indexed composite kinds. It then decoded the same immediate again to build the lowering signature. This patch reuses the first exact decoded result and calls a byte-independent checked runtime resolver. It does not add a complete-body validation pass. LLVM lazy reaches this same full compiler when a function is materialized; interpreter and pure-validator decoding are unchanged.

The reference resolver retains the exact heap, nullability and source prefix, derives the same execution carrier, checks the initialized runtime table bounds and mixed-table kind, and assigns the output only after all checks succeed. Typed function witnesses and `nofunc` are retained. The signed-blocktype resolver preserves all scalar/empty tuple forms and only borrows indexed function tuples after the runtime bounds/kind check. Successful construction clears obsolete singleton metadata. The raw emitter parser remains available and invokes the same metadata resolvers after its bounded decode. Existing full validation diagnostics and feature-check ordering remain in the first decode.

No runtime ABI, guest instruction semantics, GC synchronization or cache-policy key changes are intended. This is a compilation-path change; no compile-time or execution-speed result has been measured. Parser/context/type tuple ownership remains an initialized-module contract. A metadata helper's success is not a standalone source-validation authority.

Normative references read on 2026-10-03: [Core 3 blocktype binary grammar](https://webassembly.github.io/spec/core/binary/instructions.html#binary-blocktype), [instruction validation](https://webassembly.github.io/spec/core/valid/instructions.html), [value/reference type binary grammar](https://webassembly.github.io/spec/core/binary/types.html).

`test/0014.llvm_jit/llvm_jit_decoded_block_signature.cc` contains 45 expected component checks: scalar/shorthand/exact references; legacy and mixed runtime type tuples; struct/array indices rejected as block signatures; bounds/carrier/kind failures leaving signature metadata unchanged; truncated and overlong immediates retaining the established cursor behavior. Its synthetic owned metadata tests bounds and projection only. It does not impersonate an initialized runtime module.

Five `decoded-block-*` WAT cases in `run_wasm3_fused_validation.py` exercise actual parsed/initialized modules. The valid cases read back a non-null struct field, preserve a typed function reference, use an exception-bottom reference and execute a multi-value function block signature. The invalid case rejects a nullable value for a non-null block result. `_start` reaches every probe so lazy materialization cannot avoid validation. The existing runner performs official wasm-tools validation and compares pure/int full+lazy/LLVM full+lazy (ROS pure/int full/LLVM full) acceptance and runtime outcome. Run all five with `--only-case decoded-block-nonnull-struct --only-case decoded-block-nullable-function --only-case decoded-block-noexn --only-case decoded-block-multivalue --only-case decoded-block-nonnull-rejects-null`; retain existing truncation/type-kind/feature controls and the frozen v2 EH/value cases.

Status: source implementation and Python AST/hash review only. C++ compilation, official WAT parsing, mode parity, actual generated IR/assembly and timing remain pending the sole Linux keeper in the 64 GiB cgroup. The v1/v2 immutable snapshots are preserved. This v3 freeze carries only the new blocktype resolver delta and its focused tests; it does not imply completion of the overall Core 3 or debugger/performance task.

Revision v3-r2 preserves the two legacy `funcref`/`externref` singleton exact types as well. The original LLVM raw parser represented these as nullable abstract references; the first v3 source candidate's signed resolver discarded that metadata, so its own raw-vs-decoded component comparison would fail for those two forms. That source candidate is retained and must not be treated as a native pass.

A separate source audit exposed the same omission in pure wasm3 and interpreter blocktype construction: their old legacy singleton results had no exact type, so `block_value_matches` could fall back to carrier equality. `funcref` shares carrier 0x70 with GC references; carrier equality alone cannot prove that `any`, a struct type or GC bottom `none` is a subtype of `func`. The r2 patch preserves exact `(ref null func)` / `(ref null extern)` metadata in all three construction sites, using the existing Core 3 subtype checks. No old wasm1p1/wasm2 pure validator is edited.

Eight additional reachable WAT cases reject funcref results supplied by any/struct/none and externref results supplied by exn/GC, and accept typed function refs, `nofunc` and explicit extern/any conversions. The externref negative cases are preservation controls, not claims that their distinct old carriers were accepted. The comparison runner now includes 13 new decoded-block cases and retains its official oracle/pure/four-fused-mode decisions. These new grammar/semantic cases still await remote execution; this is source evidence of the defect and fix.
