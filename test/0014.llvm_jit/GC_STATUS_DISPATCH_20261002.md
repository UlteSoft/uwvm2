# GC success status dispatch, source candidate

The original `struct_get32` and generic aggregate lowering executes four conditional traps after its unchanged checked native call. This candidate branches once on the actual status being zero and classifies failures in a cold block. It does not bypass token membership, canonical type, foreign leases, mutable locks, input allocation, precise root snapshots, collector pauses, or retirement checks. The experimental SET32 v2 source and its frozen evidence are unchanged.

The new synchronous `llvm_jit_gc_status_dispatch_plan` resolves the original runtime trap before the getter call, or before generic root snapshot/input allocation. A failed resolution deletes its two unused blocks, restores the builder cursor, and emits no native GC call. Abandonment likewise deletes only these unpublished blocks. Once the native call executes, `commit` cannot decline or select a second helper. Generic heap-input release still executes after the native aggregate helper and before the status branch, on success and failure. Output reads and operand-stack retirement remain dominated by status zero.

Failure mapping remains status 3 → null reference; 6 → array bounds; 8/9 → GC allocation failure; every other nonzero, including unknown/high-bit values → runtime invariant failure. The cold call is the original trap from the generated frame, with the original exact function type, host calling convention, NoTail, explicit Win64 frame/stack values, memory clobber and unreachable. Static branch weights do not establish a measured performance improvement.

No new experimental macro is introduced. Every LLVM generation includes cache key `llvm-gc-status-dispatch=zero-fast-cold-v1`. The native GC bridge ABI and native symbol discriminators are unchanged. LLVM full/lazy/tiered share this translator. Interpreter and pure validator sources are unchanged. Header and module builds both consume the fragment through the existing `single_func_gc_emit.h` include; its metadata types were already imported in both translate header/module paths.

This is source-only. No compiler, native test, Wasm VM or timing was executed on macOS. Actual compile/result qualification belongs to the sole Linux keeper in the exact 64GiB, swap-zero scope. Temperature is observation only, frequency/SMT and actual CPU/cgroup ownership remain quality evidence.

Cold controls: compile and run `llvm_jit_gc_status_dispatch_ir.cc` at native O3, first SET32 undefined and then 0/2/1 (no six-profile assumption). The real emitter fixture covers mutable i32/f32 getters, signed i8/unsigned i16, generic i64 get/set, and array.new_fixed with 130 i64 inputs to exercise actual heap input allocation/free. Two integer protocol widths exercise every defined nonzero status, unknown and high-bit values. Controls include uncommitted-plan deletion with its builder in the cold block, wrong-module admission, terminated insertion block, and exact original trap declaration collision before both getter and heap-input generic emission (RV64 has no declaration and retains address/type proofs instead).

The test writes input IR, optimized IR and the actual native target object. Input IR verifies all status users/classification on the failed edge, original trap identity/type/CC/context/NoTail/clobber, success-only output reads, and exact heap-free ordering. O3 IR must have one hot comparison and no hoisted selects/classifiers in the actual GC-call block. Native disassembly must separately confirm the success path has one status guard; a branch-weight annotation alone is insufficient. Preserve failed optimized IR, do not declare success if O3 moved error classification onto the hot path. Check hardware-object architecture and actual assembly before a performance claim.

Cache unit `llvm_jit_gc_status_dispatch_cache_key.cc` must run in LLVM and tiered configurations, including SET32 undefined/0/2/1; interpreter-only must not include the LLVM key. Run new GC syntax families and null/type/bounds/allocation/invariant trap controls with fresh aligned runtime and consumers. Existing runtime objects contain compiler/environment inline definitions, so do not link a new CLI against an old runtime. The immutable S6e product and SET32 v2 historical evidence are separate baselines.

Measure unprofiled guest/wall/user/sys/frequency, whole-guest grouped hardware cycles/instructions with exact enabled/running, and VTune HW samples/uarch separately. A general allocation loop is not pure collector latency. Unknown `[ld.so.cache]` samples are not getter attribution; use actual finalized JIT object PC/range plus exact object symbol/source mapping before naming their owner.
